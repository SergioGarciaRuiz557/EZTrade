# EZTrade - Functional Demo

This walkthrough validates the complete user flow: registration, login, funds deposit, market buy, portfolio query, and notifications generated by events.

## 1. Registration

```http
POST /api/user/register
Content-Type: application/json

{
  "firstname": "Demo",
  "lastname": "User",
  "username": "demoUser",
  "email": "demo@example.com",
  "password": "password123"
}
```

The backend encodes the password and assigns `Role.USER`.

## 2. Login

Login accepts either email or username.

```http
POST /auth/login
Content-Type: application/json

{
  "email": "demo@example.com",
  "password": "password123"
}
```

Expected response:

```json
{
  "token": "<jwt>",
  "type": "Bearer"
}
```

From this point on, all protected requests use:

```http
Authorization: Bearer <jwt>
```

## 3. Deposit Funds

```http
POST /api/v1/wallet/deposit
Authorization: Bearer <jwt>
Content-Type: application/json

{
  "amount": 1000.00,
  "referenceId": "demo-deposit-001",
  "description": "Initial demo deposit"
}
```

Balance query:

```http
GET /api/v1/wallet/balance
Authorization: Bearer <jwt>
```

## 4. Query Market Data

```http
GET /api/v1/market/get-price?symbol=AAPL
Authorization: Bearer <jwt>
```

Other useful endpoints:

```http
GET /api/v1/market/search?input=apple
GET /api/v1/market/get-overview?symbol=AAPL
GET /api/v1/market/get-daily-candles?symbol=AAPL
```

## 5. Direct Market Buy

This is the recommended flow for a real buy in the current backend. The client does not send a price: `trading` queries `market :: api`, creates a BUY order, and executes it.

```http
POST /api/v1/trading/market/buy
Authorization: Bearer <jwt>
Content-Type: application/json

{
  "symbol": "AAPL",
  "quantity": 2
}
```

Internal flow:

1. `TradingMarketplaceController` receives the request.
2. `TradingService` gets the current price through `MarketPriceLookupPort`.
3. A pending BUY order is created.
4. `OrderPlacedEvent` makes wallet reserve funds.
5. `OrderExecutionRequestEvent` makes wallet settle the buy.
6. Wallet publishes `OrderExecutedEvent`.
7. Portfolio opens or increases the position.
8. Notifications generates messages through its channels.

## 6. Query Orders and Portfolio

```http
GET /api/v1/trading/orders
Authorization: Bearer <jwt>
```

```http
GET /api/portfolio
Authorization: Bearer <jwt>
```

The portfolio response includes projected cash, open positions, cost basis, realized PnL, and market valuations by symbol when prices are available.

## 7. User-to-User Marketplace

To publish a sell offer:

```http
POST /api/v1/trading/offers
Authorization: Bearer <jwt>
Content-Type: application/json

{
  "symbol": "AAPL",
  "quantity": 1,
  "price": 150.00
}
```

Main rules:

- the seller must have enough shares,
- the price cannot exceed the current market price,
- a pending offer cannot be bought by its own seller.

To list available offers:

```http
GET /api/v1/trading/offers?symbol=AAPL
Authorization: Bearer <jwt>
```

To buy another user's offer:

```http
POST /api/v1/trading/offers/{offerId}/buy
Authorization: Bearer <jwt>
```

## 8. Notifications

Notifications listens to trading, wallet, and portfolio events. The current channels are:

- email logs,
- push logs,
- WebSocket STOMP at `/user/queue/notifications`,
- persisted database inbox.

Common events in this demo:

- `ORDER_PLACED`
- `ORDER_EXECUTED`
- `PORTFOLIO_VALUATION_UPDATED`
- `INSUFFICIENT_FUNDS`, if wallet cannot reserve or settle.
